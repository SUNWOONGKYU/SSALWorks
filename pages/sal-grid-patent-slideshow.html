기존 도구의 한계 ③ — 2차원의 벽

간트 차트, 칸반 보드 — 모두 평면(2D)에 갇혀 있습니다.

2D 간트 차트

  • X축: 시간, Y축: 작업명
  • 작업 영역(Area) 정보 표현 불가
  • 의존성 계층(Level) 표현 불가
  • 수백 개 작업 → 인지적 과부하

3D SAL Grid

  • X축: Stage(단계)
  • Y축: Area(영역)
  • Z축: Level(계층)
  • 수천 개 작업도 구조적으로 파악

핵심 발상의 전환

"의존성은 코드로 선언해야 한다"
↓
"식별자가 구조를 내재하면
자동 추론할 수 있다"

종래 기술의 통념을 깨는 역발상:
이름 자체에 3차원 좌표를 담아, 별도의 코딩 없이도
순서, 의존성, 병렬성을 시스템이 자동으로 이해합니다.

SAL ID의 4가지 구성 요소

세그먼트범위의미예시
Stage1~99프로젝트 진행 단계 (X축)1=기획, 2=설계, 3=개발...
AreaAA~ZZ기능적 영역 (Y축)FE=프론트엔드, BE=백엔드...
Level1~99의존성 계층 (Z축)L1=기초작업 → L2=2차작업...
Varianta~z (선택)병렬 분기 구분a, b = 동시 실행 가능
최대 99단계 × 676영역 × 99계층 × 26분기 = 사실상 무한대의 작업을 표현 가능

이름 하나에 담긴 4가지 정보

① 절차적 순서
Stage 값이 곧 순서
S1 → S2 → S3
단계 번호만 보면 실행 순서를 안다
② 실행 의존성
같은 Stage-Area 내 Level 비교
S2BA1 → S2BA2 → S2BA3
Level이 낮은 작업이 먼저
③ 병렬성
같은 좌표 + Variant 구분
S2BA1a ∥ S2BA1b
Variant가 다르면 동시 실행 가능
④ 기능적 인접성
같은 Stage-Area = 관련 작업
S2BA1, S2BA2, S2BA3
같은 영역 작업은 공통 맥락 공유

핵심 모듈 ① — 파서 (SAL ID 해석기)

SAL ID 문자열을 받아 좌표를 추출하고 유효성을 검증합니다.

SAL ID 입력

좌표 객체
정규식: ^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$

"S2FE2a" → { stage: 2, area: "FE", level: 2, variant: "a" }
유효하지 않은 ID → Unassigned Queue로 격리 → 시스템은 멈추지 않는다

핵심 모듈 ③ — 시퀀서 (순서 자동 조정)

작업 간 Level 충돌을 감지하고, SAL ID를 자동으로 재배치합니다.

Level 충돌이란?

S2F9(후행)가 S2F1(선행)에 의존하는데, Level 9가 Level 1보다 뒤에 있어야 하는 상황
→ 시퀀서가 자동으로 S2F9를 S2F1 위치로 이동시킴

자동 재배치 동작

S2F1
S2F2
S2F3
← S2F9 이동

→ 기존 S2F1, F2, F3이 자동으로 F2, F3, F4로 밀려남 (또는 역방향 당김)

핵심 모듈 ⑦ — ID 체인 (변경 이력 추적)

SAL ID가 변경되어도 기존 참조가 끊어지지 않습니다.

블록체인 방식의 Append-Only 체인

S4BI1
→
S4BI1_S1BI2
→
S4BI1_S1BI2_S1BI3
실제 예시: Sentry 모니터링 Task가 Stage 4에서 Stage 1로 이동
→ S4BI1이 삭제되지 않고 S4BI1_S1BI2로 체인 기록
→ 마지막 세그먼트 = 최신 ID

자가 치유(Self-Healing) — 리졸버

옛날 이름으로 검색해도, 최신 작업으로 자동 안내됩니다.

① 사용자가 S4BI1 (옛 ID)로 조회 요청
② 리졸버가 체인 발견: S4BI1_S1BI2
③ 언더바(_)로 분리 → 마지막 세그먼트 추출
④ S1BI2 (최신 ID) 자동 반환
기존 참조가 깨지지 않는 참조 무결성 자가 치유 메커니즘
