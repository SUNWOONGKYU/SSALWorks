기존 기술의 구조적 한계

  • Airflow — 의존성을 task_a >> task_b 형태로 Python 코드에 직접 선언해야 함. 비개발자 접근 불가
  • Jira / Asana — 식별자(PROJECT-1234)는 순차 번호에 불과. 식별자만으로 단계·영역 파악 불가
  • 간트 차트 — 시간(X축) × 작업명(Y축)의 2차원 한계. 수천 개 작업의 입체적 관계 표현 불가
  • 공통 문제 — Task 실행과 품질 검증이 별개 시스템으로 분절 운영 → 검증 누락 구조적 발생

SAL Grid 방법론

SAL Grid는 식별자 하나에 3차원 좌표(Stage, Area, Level)를 인코딩하고, 이를 파싱하여 프로젝트 관리 구조 전체를 자동 구축하는 방법론이다.

핵심 발상: 의존성은 선언하는 것이 아니라, 식별자에서 읽어내는 것이다.
  • SAL ID 파싱 → 22개 속성의 프로젝트 그리드 자동 구축
  • Task 지시서 + 검증 지시서 동시 생성
  • 에이전트·도구 자동 배정, 9단계 사이클 자동 구동
  • 코딩 없이 식별자 하나로 프로젝트 관리 체계 완성

SAL ID 형식 정의

S{Stage}{Area}{Level}{Variant?}

  S       — 접두사 (고정)
  Stage   — 1~2자리 정수. 프로젝트 진행 단계
  Area    — 2자리 영문 대문자. 기능적 영역 코드
  Level   — 1~2자리 정수. 의존성 계층
  Variant — 소문자 a~z (선택). 병렬 분기

S2BA3 = Stage 2, Backend API, Level 3
S1FE1a = Stage 1, Frontend, Level 1, 첫 번째 병렬 분기

Jira의 PROJECT-1234(순차 번호)와 달리, 식별자를 읽는 것만으로 작업의 위치와 맥락을 즉시 파악할 수 있다.

SAL ID에 인코딩된 4가지 정보

① 절차적 순서
Stage 값 대소 비교로 순서 자동 결정
S1 → S2 → S3
② 실행 의존성
동일 Stage-Area 내 Level 비교로 선후 관계 추론
S2BA1 → S2BA2 → S2BA3
③ 병렬성
Variant(a, b, c)로 병렬 실행 판별
S2BA1a와 S2BA1b 동시 수행
④ 기능적 인접성
동일 Stage-Area 조합의 Task는 같은 맥락 공유
S2BA1, S2BA2, S2BA3 = 같은 기능군

SAL ID 파싱 정규식

^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$
  • 캡처 그룹 1: Stage — 캡처 그룹 2: Area — 캡처 그룹 3: Level — 캡처 그룹 4: Variant
  • 정규식 하나로 유효성 검증 + 구성요소 추출 동시 수행
  • 이후 범위 검사 → Area 코드 등록 확인 → 고유성 검사 → 정규화된 좌표 객체 생성
이 파싱이 SAL Grid 방법론의 출발점이다. 문자열 → 구조화된 좌표 변환 → 프로젝트 그리드 자동 구축 시작.

3차원 좌표계 ① Stage 축

프로젝트의 시간적 진행 단계. 1~99 범위 정수.

  • 낮은 숫자 = 초기 단계, 높은 숫자 = 후기 단계
  • SW 개발: S1=기획, S2=설계, S3=개발, S4=테스트, S5=배포
  • 건설: S1=설계, S2=조달, S3=시공, S4=검수, S5=인도
Stage 값의 대소 비교만으로 프로젝트 전체의 절차적 순서가 자동 결정된다. 별도 일정표 불필요.

3차원 좌표계 ② Area 축

프로젝트 내의 기능적 영역. 2자리 영문 대문자 코드.

  • FE(Frontend), BE(Backend), QA, SE(Security), DA(Data) 등 최대 676개(26×26) 정의 가능
  • Area 코드 → 에이전트 자동 배정 기준 (FE → frontend-developer, SE → security-specialist)
  • 작업 에이전트 ≠ 검증 에이전트 — 작성자 ≠ 검증자 원칙 구조적 강제

3차원 좌표계 ③ Level 축

동일 Stage-Area 셀 내에서 의존성과 수행 순서를 결정하는 축.

  • Level 작은 값 = 선행, 큰 값 = 후행. S2BA1 → S2BA2 → S2BA3
  • 같은 Area 내: Level 비교로 자동 추론
  • 다른 Area 간: dependencies 필드로 명시적 선언
  • 자동 추론 + 명시적 선언의 이중 구조

Stage × Area 매트릭스

모든 작업은 Stage(X축) × Area(Y축) 2차원 매트릭스 위에 배치된다.

  • Stage 범위 + Area 범위 정의 → 매트릭스 셀(교차점)이 작업 영역
  • 각 셀 안에서 Level + Variant 부여 → SAL ID 확정
  • 매트릭스를 그리고, Task를 배치하고, SAL ID를 부여하면 → 나머지는 시스템이 자동 구축
SSAL Works 적용 사례: 5 Stage × 11 Area = 55 셀, 총 71개 Task 운영 중

핵심 차별점 ① 의존성 자동 추론

기존 워크플로우 시스템은 의존성을 사람이 직접 선언해야 한다. SAL Grid는 이 전제를 뒤집는다.

  • Airflow: Task 100개면 의존성 코드 100줄 이상 수동 작성
  • SAL Grid: S2BA1, S2BA2, S2BA3 ID만 부여하면 Level 비교로 순서 자동 결정
  • S1 모든 Task는 S2 Task보다 선행 — Stage 비교로 자동 추론
"의존성 선언을 자동화"한 것이 아니다. 의존성이라는 개념 자체를 식별자의 구조적 속성으로 치환한 것이다.

핵심 차별점 ① Airflow와의 결정적 차이

Apache Airflow

  • DAG를 Python 코드로 작성
  • task_a >> task_b 수동 선언 필수
  • 프로그래밍 지식 필수
  • 식별자에 구조 정보 없음
VS

SAL Grid

  • SAL ID 부여만으로 의존성 추론
  • 코딩 불필요
  • 비개발자도 즉시 활용
  • 식별자에 3차원 좌표 인코딩

Task 지시서와 검증 지시서가 동시에 생성되므로, 검증 기준이 누락될 구조적 가능성이 사라진다.

핵심 차별점 ③ ID 체인 — Append-Only

SAL ID가 변경되어도 기존 ID를 삭제하지 않고 뒤에 연결하여 이력을 보존한다.

S4BI1 → S1BI2로 변경 시:  S4BI1_S1BI2
한 번 더 변경 시:          S4BI1_S1BI2_S1BI3
마지막 세그먼트 = 최신 ID, 체인 전체 = 변경 이력
  • 추가만 가능, 삭제·수정 불가 — 블록체인과 동일 원리
  • 변경 이력의 위변조가 구조적으로 불가능

핵심 차별점 ③ 리졸버 — 자가 치유

구(Old) SAL ID로 조회해도, 리졸버가 체인을 순회하여 최신 ID를 자동 반환한다.

  • Jira: Issue 이동 시 기존 참조 링크 전부 깨짐 → 수동 복구 필요
  • SAL Grid: S4BI1로 조회 → 리졸버가 체인 순회 → S1BI3(최신) 자동 반환
참조 무결성의 자가 치유(Self-Healing Referential Integrity) — 프로젝트 구조가 아무리 변경되어도, 한 번 생성된 참조는 영구 유효.

핵심 차별점 ④ 실행-검증 일체화

Task 완료와 동시에 검증이 자동 트리거되며, 작성자 ≠ 검증자 분리 배정.

  • 기존: Jira에서 "완료" → 별도 QA 도구 → 결과를 다시 Jira에 기록 (검증 누락 빈번)
  • SAL Grid: Executed 상태 전환 → 검증 에이전트 자동 투입 → 결과 실시간 기록
  • Verified 아닌 Task는 Completed 전환 불가 — 시스템이 강제

핵심 차별점 ④ Stage Gate

개별 Task 검증에 더하여, Stage 단위 최종 승인 절차가 존재한다.

  • Stage 내 모든 Task Completed 확인
  • 전체 빌드·테스트 통과 확인
  • 의존성 체인 완결성 + 차단 요소 확인
  • 승인 → 다음 Stage 진입 / 거절 → Task 실행 단계로 자동 회귀
Jira에는 Stage Gate 개념이 없다. "Done"으로 옮기면 끝. SAL Grid의 Stage Gate는 시스템 레벨에서 강제되는 품질 관문이다.

왜 기존 기술로 도달할 수 없는가

  • 기존 통념: "의존성은 코드로 선언해야 한다" — Airflow 문서, 논문, 상용 도구 전반의 암묵적 전제
  • 기존 개선 방향: 의존성 선언을 "더 편하게", "더 직관적으로" → 선언 자체를 없앤다는 발상에 도달 불가
  • SAL Grid의 접근: 식별자에 좌표를 인코딩하고, 좌표의 대소 비교로 의존성을 추론 → 식별자가 자기 설명적 객체로 재정의됨
이것은 점진적 기술 개선이 아니라, 설계 패러다임의 전환이다.

사이클 ①~③ 계획 → ID 생성 → 그리드 구축

  • ① 계획: Stage × Area 매트릭스에서 필요한 작업 선정
  • ② ID 생성: SAL ID 가확정(Provisional) → 의존성 검증 → 최종 확정(Finalization)
  • ③ 그리드 구축: 정규식 파싱 → 범위 검사 → 코드 유효성 → 고유성 → 22개 속성 자동 생성
이 세 단계를 거치면 코딩 한 줄 없이 프로젝트의 실행-검증 체계가 완성된다.

사이클 ④~⑥ 실행 → 검증 → 기록

  • ④ 실행: 에이전트가 지시서에 따라 작업 수행. 상태·진행률·산출물 실시간 추적
  • ⑤ 검증: Executed 상태 전환 즉시 검증 에이전트 자동 투입. 수동 개입 불필요
  • ⑥ 기록: 실행·검증 결과를 원자적 쓰기(Atomic Write)로 기록. 부분 기록 방지
실행과 검증 사이에 인간의 개입이 없다. Task 완료 → 검증 → 기록이 하나의 연속 자동 프로세스.

사이클 ⑦~⑨ Stage 검증 → 리포트 → 승인

  • ⑦ Stage 검증: Stage 내 모든 Task 완료·검증 여부 + 빌드·테스트 + 의존성 체인 종합 확인
  • ⑧ 리포트: Stage 검증 결과를 구조화된 문서로 자동 생성
  • ⑨ 승인: 승인 → 다음 Stage 사이클 시작 / 거절 → ④단계 자동 회귀
피드백 루프가 내장되어, 결함이 있는 상태로 다음 Stage 진입이 구조적으로 불가능하다.

    Stage·Level 값 비교만으로 실행 순서 자동 결정. 선행 사례 없음.
  2. 식별자 하나로 프로젝트 관리 체계 전체가 자동 구축된다.
    22개 속성 그리드 + 지시서 + 검증 지시서 + 에이전트 배정 동시 완성.
  3. 한 번 생성된 참조는 영구적으로 유효하다.
    Append-Only ID 체인 + 리졸버 자동 리디렉트. 참조 깨짐 구조적 불가.
  4. 실행과 검증이 하나의 연속된 자동 프로세스이다.
    Task 완료 → 검증 자동 트리거 → Stage Gate 승인. 시스템 레벨 강제.
