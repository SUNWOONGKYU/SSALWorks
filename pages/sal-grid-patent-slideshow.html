기존 프로젝트 관리 기술의 구조적 한계

  • 코딩 의존적 워크플로우 — Apache Airflow 등은 DAG 구조를 Python 코드로 직접 작성해야 하며, 의존성 변경 시 코드 수정과 디버깅 필수. 비개발자 접근 불가
  • 식별자의 구조 정보 부재 — Jira(PROJECT-1234), Asana 등의 식별자는 자동 증가 순차 번호에 불과. 어떤 단계, 어떤 영역의 작업인지 식별자만으로 파악 불가. 별도 매핑 테이블 조회 필수
  • 참조 무결성 위반 — 작업 속성 변경 시 기존 식별자가 무효화되거나 참조 링크 깨짐. 변경 이력을 텍스트 로그로만 관리하여 역추적 고비용
  • 2차원 시각화의 한계 — 간트 차트는 시간(X)과 작업명(Y)의 2차원 평면에 한정. 수천 개 작업의 입체적 위상을 평면으로 억지 병합(Flatten)할 수밖에 없는 구조
  • 실행-검증 프로세스 단절 — Task 실행과 품질 검증이 별개 도구로 분절 운영. 검증 누락, 피드백 지연 빈발. 체계적 오케스트레이션 사이클 부재

발상의 전환

종래 기술의 통념: "의존성은 코드로 명시해야 한다"
본 발명의 역발상: "식별자 자체가 구조 정보를 내재하면, 명시적 선언 없이 자동 추론 가능"

기존의 모든 워크플로우 시스템은 의존성을 task_a >> task_b 형태로 수동 코딩하는 것을 당연한 전제로 삼아 왔음. 해당 기술 분야의 공식 문서와 주요 논문 모두 이 전제에서 출발

본 발명은 이 통념을 깨고, 식별자 자체에 3차원 좌표(Stage, Area, Level)를 인코딩하여 파싱만으로 의존성 구조를 자동 구축하는 No-Code 방식을 최초로 제안

SAL ID = Self-Descriptive Identifier. 식별자 하나에 작업의 단계, 영역, 계층, 병렬 분기 정보가 모두 내재된 자기 설명적 식별자

SAL ID 형식 정의

S{Stage}{Area}{Level}{Variant?}

  S   — 접두사 (SAL ID 식별자, 고정)
  Stage  — 1~2자리 정수 (1~99). 프로젝트 진행 단계
  Area   — 2자리 영문 대문자. 기능적 영역 코드 (FE, BE, QA 등)
  Level  — 1~2자리 정수 (1~99). 의존성 계층 (작을수록 선행)
  Variant — 소문자 a~z (선택). 동일 좌표 내 병렬 작업 구분

실제 예시

SAL IDStageAreaLevelVariant해석
S1FE11FE1-Stage 1, Frontend, 최우선 작업
S2BE22BE2-Stage 2, Backend, Level 2 후행 작업
S1FE1a1FE1aS1FE1 좌표의 첫 번째 병렬 분기
S10DA5c10DA5cStage 10, Data, Level 5, 세 번째 병렬 분기

SAL ID에 인코딩된 4가지 정보

1. 절차적 순서

Stage 값이 작을수록 먼저 수행되는 단계. S1 → S2 → S3 순서가 Stage 값 파싱만으로 자동 결정. 별도 시간표 불필요

2. 실행 의존성

동일 Stage-Area 내에서 Level 값의 크고 작음이 선후 관계 결정. S2BA1 → S2BA2 → S2BA3 — dependencies 필드 명시 없이도 Level 비교로 자동 추론

3. 병렬성

동일 (Stage, Area, Level) 좌표에 Variant(a, b, c)가 부여되면 병렬 실행 가능. S2BA1a || S2BA1b — Variant 유무 확인만으로 즉시 판별

4. 기능적 인접성

동일 Stage-Area 조합의 Task는 같은 기능적 맥락 공유. S2BA1, S2BA2, S2BA3 모두 "Stage 2의 Backend API 구현"이라는 맥락에 속함

핵심: SAL ID는 단순 참조 번호가 아닌, 절차적 순서·실행 의존성·병렬성·기능적 인접성이 구조적으로 내재된 자기 설명적(Self-Descriptive) 식별자

SAL ID 파싱 정규식

파서 모듈(40)이 SAL ID를 해석하는 데 사용하는 정규 표현식

^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$
패턴캡처 대상설명
^S접두사SAL ID 식별 고정 문자
(\d{1,2})Stage1~2자리 정수 (1~99)
([A-Z]{2})Area대문자 알파벳 2자리 코드
(\d{1,2})Level1~2자리 정수 (1~99)
([a-z])?Variant소문자 1자리 (선택적)
이 정규식 하나로 SAL ID의 유효성 검증과 구성요소 추출을 동시 수행. 형식 불일치 시 Unassigned Queue(46)로 격리하여 시스템 흐름 보호

3차원 좌표계 ① Stage 축 (X)

프로젝트의 시간적 진행 단계. 1~99 범위의 정수 값

낮은 숫자가 초기 단계, 높은 숫자가 후기 단계를 의미. 도메인에 따라 재정의 가능

소프트웨어 개발

  • S1: 기획 — 요구사항 정의, 범위 설정
  • S2: 설계 — 아키텍처, 상세 설계
  • S3: 개발 — 구현, 코딩
  • S4: 테스트 — 단위, 통합 테스트
  • S5: 배포 — 스테이징, 프로덕션

제조/건설

  • S1: 설계
  • S2: 조달
  • S3: 조립/시공
  • S4: 검수
  • S5: 인도/완공
Stage 값의 대소 비교만으로 프로젝트 전체의 절차적 순서가 자동 결정 — 별도 일정표 없이도 실행 순서 추론 가능

Area 코드표는 프로젝트 초기에 정의. 최대 26x26 = 676개 고유 Area 정의 가능 (실무상 10~30개가 일반적)

3차원 좌표계 ③ Level 축 (Z)

작업 간 의존성과 수행 순서의 계층. 1~99 범위 정수

  • Level 값이 작은 Task = 선행 작업, 큰 Task = 후행 작업
  • 동일 Stage-Area 내에서 Level이 낮은 작업이 완료되어야 높은 Level 작업 시작 가능
  • Level 1: 해당 셀에서 가장 먼저 수행되는 기초 작업
  • Level 2, 3, ...: 순차적으로 의존하는 후행 작업
의존성 자동 추론의 핵심: S2BA1 → S2BA2 → S2BA3 순서는 Level 값의 대소 비교만으로 결정. dependencies 필드에 명시적 선언이 없어도 파서(40)가 자동으로 선후 관계를 추론

서로 다른 Area 간의 의존성은 별도 속성(dependencies 필드)으로 명시적 선언 — 같은 Area 내 Level 기반 자동 추론과 보완적 관계

Stage × Area 매트릭스 기반 Task 선정

SAL ID 생성에 앞서, 모든 작업은 Stage(X)와 Area(Y)로 구성된 2차원 매트릭스에서 선정

  1. Stage 범위 결정 — 프로젝트를 몇 개의 단계로 구성할지 정의
  2. Area 범위 결정 — 관리할 기능 영역을 코드로 정의
  3. 매트릭스 상 위치 선정 — 각 Task가 속할 Stage와 Area 결정
  4. Level 및 Variant 부여 — 같은 셀 내 우선순위와 병렬 구분
  5. SAL ID 생성 — 위 정보를 인코딩하여 최종 식별자 확정
실적용 사례: SSAL Works 프로젝트 — 5개 Stage × 11개 Area = 5×11 매트릭스로 총 71개 Task 관리. Stage별 분포: S1(9개), S2(17개), S3(11개), S4(21개), S5(13개)

엔진 계층 — 4개 모듈의 순차 처리

입력된 SAL ID가 실행 가능한 프로젝트 그리드로 변환되는 핵심 처리 과정

SAL ID 수신→ 파서(40)→ 그리드 생성기(52)→ 시퀀서(53)→ 배분기(54)
  • 파서(40) — 정규식 매칭 → 범위 검사 → 코드 유효성 검사 → 고유성 검사 → 정렬 키 생성. 총 5단계 검증을 거쳐 정규화된 좌표 객체 생성
  • 그리드 생성기(52) — 파싱된 좌표 정보로 Task 지시서(수행 지침, 완료 조건, 기술 스택)와 검증 지시서(검증 기준, 테스트 명령, 통합 검증)를 자동 생성
  • 시퀀서(53) — 전체 Task의 dependencies를 분석하여 Level 충돌 감지 및 SAL ID 자동 조정. 기존 Task들의 Level 값을 밀어내거나 당겨서 순서 재배열
  • 배분기(54) — Area 코드 기반으로 Task 에이전트와 검증 에이전트를 분리 배정. 작성자 ≠ 검증자 원칙 강제

핵심 모듈 ① 파서(40)

불완전한 문자열을 실행 가능한 정규화된 좌표 객체로 변환하는 엔진

5단계 검증 프로세스

  1. 정규식 매칭 (Lexical Analysis) — ^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$ 패턴과 일치 여부 확인. 불일치 시 즉시 예외 처리로 분기
  2. 범위 검사 (Range Validation) — Stage, Level 값이 유효 범위(1~99) 내인지 확인
  3. 코드 유효성 검사 (Semantic Validation) — Area 코드가 Area_Code_Master 테이블에 등록된 코드인지 확인
  4. 고유성 검사 (Uniqueness Check) — (Stage, Area, Level, Variant) 조합 중복 여부 확인
  5. 정렬 키 생성 (Sort Key Generation) — 02_FE_02_a 형식의 정렬 키 생성. 실행 순서 자동 결정에 활용
검증 실패 시 Unassigned Queue(46)로 격리 — 시스템 전체 흐름 중단 없이 오류를 별도 관리. 관리자가 수동으로 재정의하거나 해결하는 안전장치

핵심 모듈 ② 시퀀서(53)

Level 충돌 감지 및 SAL ID 동적 조정

Task 간 의존성 관계를 분석하여, Level 값의 순서가 실제 의존 관계와 불일치하는 경우를 자동으로 감지하고 해결

처리 절차

  1. 전체 Task 지시서의 dependencies 필드 파싱 → 각 Task의 선행/후행 Task 목록 추출
  2. 선행-후행 관계에서 Level 값의 크고 작음이 일치하는지 검사. 후행 Task의 Level이 선행보다 작으면 Level 충돌으로 판정
  3. 충돌 감지 시 해당 Task를 원하는 Level로 이동. 이동 대상 Level 이상의 기존 Task들의 Level 값을 1씩 자동 증가(밀어내기), 또는 빈 Level 구간의 Task들을 1씩 감소(당기기)
Apache Airflow와의 차이: Airflow에서는 DAG 구조 변경 시 수동으로 코드를 수정하고 디버깅해야 함. 본 발명의 시퀀서는 Level 값 조정만으로 의존성 구조를 자동 재배열

핵심 모듈 ③ 배분기(54)

Area 코드 기반 에이전트 및 도구 자동 배정

배정 원칙

  • Task 에이전트와 검증 에이전트의 분리 배정 — 작성자와 검증자가 동일하면 검증의 객관성이 훼손되므로, 반드시 다른 역할군에서 배정
  • Execution Type 기반 분기 — AI-Only(AI 에이전트만), Human-AI(사람+AI), Manual(사람만)으로 구분하여 배정
  • 도구 자동 배분 — Task 지시서의 tools 필드에 명시된 도구 목록을 에이전트에게 자동 제공

체인 구조

SAL ID 변경 시 기존 ID를 삭제하지 않고, 언더바(_) 구분자로 새 ID를 뒤에 연결

S4BI1 → S4BI1_S1BI2 → S4BI1_S1BI2_S1BI3
         ↑ 최초      ↑ 1차 변경       ↑ 2차 변경
마지막 세그먼트(S1BI3)가 항상 최신 SAL ID

리졸버(74)의 자가 치유 메커니즘

  • 외부 시스템이 구(Old) SAL ID(S4BI1)로 조회 요청
  • 리졸버가 체인을 순회하여 마지막 세그먼트(S1BI3)를 최신 ID로 반환
  • 사용자는 SAL ID 변경 사실을 인지하지 못한 채 정상 조회 가능
참조 무결성 자가 치유(Self-Healing) — Jira 등에서 Issue 번호 변경 시 발생하는 참조 링크 깨짐 문제를 원천 해소. 추가만 가능하고 삭제/수정 불가(Append-Only)

핵심 모듈 ⑦ 그리드 생성기(52) — 지시서 자동 생성

파싱된 좌표 정보로 Task 지시서와 검증 지시서를 동시 생성

  • Prerequisites (선행 조건)
  • Specific Instructions (구체적 수행 지침)
  • Expected Output Files (산출물)
  • Completion Criteria (완료 기준)
  • Tech Stack, Agent, Tools, Execution Type

  • Test Commands (테스트 명령)
  • Build Verification (빌드 검증)
  • Integration Verification (통합 검증)
Task 지시서와 검증 지시서가 동시에 생성되어 실행-검증 일체화의 기반이 됨

9단계 오케스트레이션 사이클

계획 수립부터 Stage 승인까지 — 실행·검증·기록·승인의 순환적 사이클

① 계획 수립→ ② SAL ID 생성→ ③ 그리드 구축→ ④ Task 실행→ ⑤ 검증 수행→ ⑥ 결과 기록→ ⑦ Stage 검증→ ⑧ 리포트 생성→ ⑨ Stage 승인
피드백 루프 내장: Stage 승인 거절 시 → ④ Task 실행 단계로 자동 회귀하여 수정 후 재실행. Stage 승인 완료 후 → 다음 Stage에 대해 동일 사이클 반복

각 Task 완료 시 자동으로 검증이 트리거되고, 검증 결과가 실시간 기록됨. Stage 단위의 최종 승인 없이는 다음 단계 진행 불가

사이클 ①~③ 계획 → 생성 → 구축

① 계획 수립 (81)

Stage × Area 매트릭스 상에서 프로젝트에 필요한 Task를 선정. 각 Task에 Level 및 Variant 부여

② SAL ID 생성 (82)

선정된 Task의 Stage, Area, Level, Variant 정보를 인코딩하여 고유한 SAL ID 생성. Provisional(가확정) → 의존성 검증 → Finalization(확정) 프로세스를 거침

③ SAL 그리드 구축 (83)

  • 파서(40) — SAL ID 파싱, 3차원 좌표 추출, 5단계 검증
  • 그리드 생성기(52) — Task 지시서 + 검증 지시서 자동 생성
  • 시퀀서(53) — Level 충돌 감지 및 SAL ID 동적 조정
  • 배분기(54) — 에이전트 및 도구 자동 배정
이 3단계를 거치면 22개 속성으로 구성된 프로젝트 SAL 그리드가 완성 — 코딩 없이 자동 구축

사이클 ④~⑥ 실행 → 검증 → 기록

④ Task 실행 (84)

배정된 Task 에이전트가 Task 지시서에 따라 작업 수행. 상태 변화(Status), 진행률(Progress), 산출물(Artifacts), 소요 시간(Duration) 등 동적 속성을 실시간 추적

⑤ 검증 수행 (85)

작업 완료 즉시 검증 에이전트가 자동 투입. 테스트 결과, 빌드 성공 여부, 코드 품질을 검증 지시서에 따라 검증. Task 에이전트와 검증 에이전트는 반드시 분리 배정

⑥ 결과 기록 (86)

SAL 그리드 레코더(60)가 실행 및 검증 결과를 원자적 쓰기(Atomic Write)로 실시간 기록. 기록 데이터: SAL ID, 이벤트 유형, 소요 시간, 산출물, 테스트/빌드 결과, 특이사항

실행-검증 일체화(Quality Assurance Loop): Task 완료와 동시에 검증이 자동 트리거되는 강결합 프로세스. 결함 전파를 원천 차단하고 산출물 무결성 보장

사이클 ⑦~⑨ Stage 검증 → 리포트 → 승인

⑦ Stage 검증 (87)

  • 해당 Stage 내 모든 Task 완료 여부 확인
  • 전체 빌드 및 테스트 통과 여부 확인
  • 의존성 체인 완결성 확인 (순환 의존성, 미해결 의존성 없음)
  • 산출물 생성 여부 및 차단 요소(Blockers) 존재 여부 확인

⑧ 리포트 생성 (88)

Stage 완료 현황, 빌드 검증, 테스트 검증, 의존성 체인 검증, 산출물 검증, 차단 요소, 종합 판정, 다음 Stage 준비 상태를 포함하는 검증 리포트 자동 생성

⑨ Stage 승인 (89) — Stage Gate

생성된 리포트 기반으로 다음 Stage 진입 여부 최종 결정. 승인 시 다음 Stage 사이클 시작. 거절 시 ④ Task 실행 단계로 자동 회귀하여 수정 후 재실행하는 피드백 루프 내장

선행기술 대비 ① Apache Airflow와의 차별성

Apache Airflow

  • DAG 구조를 Python 코드로 명시적 작성
  • task_a >> task_b 형태의 수동 의존성 코딩
  • 반복문, 조건문, 함수 등 고급 프로그래밍 지식 필요
