【발명의 명칭】
【국문명】
3차원 좌표계(Stage-Area-Level)가 인코딩된 식별자 기반으로 생성하는 프로젝트 그리드를 활용한 멀티태스크 오케스트레이션 시스템 및 방법
【영문명】
Multi-Task Orchestration System and Method Utilizing Project Grid Generated Based on Identifiers Encoding 3D Coordinate System (Stage-Area-Level)

【기술분야】
본 발명은 프로젝트의 단계(Stage), 영역(Area), 계층(Level)을 나타내는 3차원 좌표 정보가 인코딩된 식별자(이하 "SAL ID"라 한다)를 기반으로, 22개 속성으로 구성된 프로젝트 그리드(이하 "SAL Grid"라 한다)를 생성하고, 이를 활용하여 멀티태스크를 자동 오케스트레이션하는 시스템 및 방법과 관련된 것임.

본 발명은 국제특허분류(IPC) 기준으로 G06F 9/46(다중 프로그래밍 배열), G06F 9/48(프로그램 실행 제어), G06Q 10/06(자원, 워크플로우 및 프로젝트 관리) 분야에 해당함.

본 발명의 핵심은 종래의 "그래프(DAG)를 수동으로 코딩하는 방식"에서 탈피하여, "3차원 좌표가 인코딩된 식별자(SAL ID)를 파싱하여 프로젝트 그리드(SAL Grid)를 자동 생성하는 방식"으로 패러다임을 전환하는 것임. 이를 통해 작업 지시서 및 검증 지시서의 자동 생성, 3D 시각화, 변경 이력의 불변 보존(ID Chain)을 가능하게 한다.

【발명의 배경이 되는 기술】
1. 종래 기술의 개요
본 발명이 속하는 기술 분야의 종래 기술은 크게 세 가지 범주로 분류됨.

가) 워크플로우 오케스트레이션
워크플로우 오케스트레이션(Workflow Orchestration)은 복수의 작업(Task) 간의 의존 관계를 자동 실행 및 관리하는 기술이다. Apache Airflow, Prefect, Temporal 등이 대표적이며, 이들은 주로 DAG(Directed Acyclic Graph)를 핵심 시스템 구조로 사용한다. 사용자가 코드(Python 등)로 명시적으로 코딩하면, 이들이 이를 파싱하여 스케줄링하고 실행하는 구조를 갖는다.

나) 프로젝트 관리 도구
Jira, Asana, Monday.com, Microsoft Project 등의 프로젝트 관리 도구는 작업을 리스트(List), 칸반(Kanban), 간트 차트(Gantt Chart) 형태로 관리한다. 이들 도구에서 사용하는 식별자(예: PROJECT-1234)는 순차적으로 부여되는 단순 참조 번호로서, 작업의 계층적 구조나 관리 정보를 포함하지 않는다.

다) 좌표 기반 태스크
3차원 좌표계는 CAD, GIS, 게임 엔진 등에 객체의 공간적 위치를 표현하는 데 널리 사용된다. 과거 유사 기술 연구에서는 다중 프로젝트 스케줄링을 위해 3차원 간트 차트를 제안하기도 하였으나, 이는 시각화 목적에 한정되며 식별자 자체에 시스템적 자동 구조 추출과는 무관하다.

2. 종래 기술의 문제점
상기 선행기술들은 다음과 같은 공통적인 문제점들을 갖는다.

가) 코딩 복잡성
종래의 워크플로우 태스크(Apache Airflow 등)는 DAG(Directed Acyclic Graph)를 활용하려면 코드를 직접 코딩해야 한다. 수백~수천 개의 작업과 의존 관계를 수동으로 작성해야 하므로 작성 비용이 높고, 오류 발생이나 순환 참조 문제가 빈번하다.

나) 식별자의 구조 정보 부재
종래의 프로젝트 관리 도구(Jira, Asana 등)에서 사용하는 식별자(예: PROJECT-1234)는 순차적으로 부여되는 단순 참조 번호에 불과하다. 작업의 단계(Stage), 영역(Area), 계층(Level) 등 위치 정보를 포함하지 않아, 식별자만으로는 작업의 맥락이나 의존 관계를 파악하기 어렵다.

다) 이력 추적의 어려움
작업의 위치나 속성이 변경되더라도 이전 상태에 대한 기록이 없어 추적성(Traceability)이 약화된다. 문제 발생 시 원인 규명, 책임 소재 파악, 과거 상태 복원이 어렵다.

라) 시각화의 한계
2D 간트 차트나 매트릭스 형태의 그리드로는 Stage, Area, Level 등 다차원 정보를 표현하는 데 한계가 있어 정보 손실이 발생하고, 복잡한 프로젝트의 전체 구조를 직관적으로 파악하기 어렵다.

마) 시스템 간 비일관성
소프트웨어 개발, 제조, 건설 등 시스템마다 각기 다른 시스템이 식별 체계를 사용하여 통합 관리 및 정보 교환에 비용이 발생한다.



3. 선행기술과의 차별점
본 발명은 상기 종래 기술의 문제점들을 해결하기 위해, 다음과 같은 차별화된 접근 방식을 제시한다.

가) 코딩 방식: 종래 기술이 DAG를 코드로 수동 코딩해야 하는 반면, 본 발명은 SAL ID를 파싱하여 자동으로 구조를 생성한다.
나) 식별자: 종래 기술의 식별자는 단순 번호로서 구조 정보를 포함하지 않지만, 본 발명의 SAL ID는 3차원 좌표(Stage-Area-Level)가 인코딩되어 있다.
다) 그리드 생성: 종래 기술이 그리드를 수동으로 구성해야 하는 반면, 본 발명은 SAL ID를 기반으로 22개 속성의 프로젝트 그리드를 자동 생성한다.
라) 이력 관리: 종래 기술이 별도 프로세스가 필요하거나 이력이 불완전한 반면, 본 발명은 ID Chain을 통해 변경 이력을 불변(Append-Only) 보존한다.
마) 시각화: 종래 기술이 2D 간트 차트 또는 매트릭스 형태의 그리드를 사용하는 반면, 본 발명은 3D Grid(Stage×Area×Level)를 통해 다차원 정보를 직관적으로 표현한다.
바) 시스템 간 적용: 종래 기술이 시스템별도 별도 도구를 사용하는 반면, 본 발명은 범용 인터페이스를 통해 다양한 시스템에 통합 적용 가능하다.
사) 참조 해석: 종래 기술이 참조가 고정되어 변경 시 무효화되는 반면, 본 발명은 리졸버(Resolver)를 통해 최신 ID를 자동으로 해석한다.

【발명의 효과】
【해결하려는 과제】
본 발명은 상기 종래 기술의 문제점들을 해결하기 위해 고안된 것으로서, 다음과 같은 기술적 과제를 해결하고자 한다.

가) 구조 정보가 내재된 식별자의 부재
종래 기술의 식별자(예: PROJECT-1234)는 순차적으로 부여되는 단순 참조 번호에 불과하여, 작업의 단계(Stage), 영역(Area), 계층(Level) 등 구조 정보를 포함하지 않는다. 본 발명은 3차원 좌표 정보 자체가 인코딩된 새로운 형식의 식별자(SAL ID)를 제안함으로써, 식별자만으로 작업의 위치, 맥락, 의존 관계를 즉시 파악할 수 있도록 한다.

나) 수동 DAG 코딩의 복잡성
종래 기술에서는 워크플로우 구조(DAG)를 활용하려면 코드를 수동으로 코딩해야 한다. 본 발명은 SAL ID를 파싱하는 것만으로 프로젝트 그리드를 자동 생성함으로써 코딩의 복잡성을 해소한다.

다) 다차원 정보의 시각화 한계 (인지적 병목)
종래 기술의 2D 간트 차트는 단계/영역/계층 등 다차원 정보를 표현하는 데 한계가 있어 정보 손실이 발생한다. 본 발명은 Stage×Area×Level의 3D Grid를 통해, 복잡한 프로젝트 구조를 3차원 공간으로 매핑하여 관리자가 전체적인 진행 상황과 작업 간의 유기적 관계를 한눈에 파악(Overview)할 수 있는 시각적 통찰력을 제공한다.

【과제의 해결 수단】
본 발명은 상기 과제를 해결하기 위해, 다음과 같은 프로세스를 제공한다.

가) SAL ID (식별자)
본 발명의 핵심은 3차원 좌표 정보가 인코딩된 식별자인 SAL ID이다. SAL ID는 Stage(단계), Area(영역), Level(계층), Variant(변형)의 4개 세그먼트로 구성되며, 식별자 자체에 작업의 3차원 좌표 위치가 명시적으로 표현된다. 이를 통해 식별자만으로 해당 작업이 프로젝트의 어느 단계, 어느 영역, 어느 계층에 위치하는지 즉시 파악할 수 있다.

나) SAL Grid (프로젝트 그리드)
SAL ID가 파싱되면, SAL 그리드 생성기(52)가 복수의 속성 그룹(일 실시예로 22개 속성)으로 구성된 프로젝트 그리드(SAL Grid)를 자동 생성한다. 이 속성들은 기본 정보, 작업 지시, 작업 실행, 검증 지시, 검증 실행, 검증 완료 등의 그룹으로 분류될 수 있으며, 구체적인 속성의 개수와 종류는 프로젝트의 성격에 따라 유연하게 정의될 수 있다.

다) 멀티태스크 오케스트레이션 시스템
생성된 SAL Grid를 기반으로, 계획 수립 → SAL ID 생성 → 그리드 구축 → 작업 실행 → 검증 수행 → 결과 기록 → Stage 검증 → 보고서 생성 → Stage 승인의 9단계 순환 프로세스가 진행된다.

라) SAL ID 체인 (보조 기능)
작업의 위치 이동이나 변경 시 SAL ID 체인(70)을 통해 변경 이력을 불변(Append-Only) 방식으로 보존한다. 리졸버(74)를 통해 과거 SAL ID로부터 최신 SAL ID를 자동으로 해석할 수 있다.

【발명의 효과】
본 발명은 이러한 프로세스를 통해 다음과 같은 효과를 제공한다.

가) 식별자의 자기 설명성(Self-Describing Identifier)
SAL ID는 그 자체로 작업의 3차원 좌표(Stage-Area-Level)를 표현하므로 별도의 조회 없이 식별자만으로 작업의 위치와 맥락을 즉시 파악할 수 있다. 이는 종래의 단순 번호 식별자가 제공할 수 없는 본질적인 차별점이다.

나) 프로젝트 그리드의 자동 생성
SAL ID를 파싱하는 것만으로 22개 속성의 프로젝트 그리드를 Task 지시서, 검증 지시서와 함께 자동으로 생성한다. 이를 통해 수백 개의 작업에 대해 개별적으로 의존관계를 정의해야 했던 기존 오케스트레이션 도구(Jira, Airflow)의 비효율을 제거하고, 입력 단계의 비용을 획기적으로 절감하는 효과를 제공한다.

다) 체계적인 워크플로우 프로세스
계획부터 승인까지의 9단계 순환 프로세스가 확립되어, 프로젝트의 시작부터 완료까지 체계적인 통제 및 관리가 가능하다.

라) 다양한 시스템에 범용 적용 (도메인 확장성)
산업 분야의 특성에 맞춰 좌표축(Axis)의 정의를 유연하게 커스터마이징함으로써, 소프트웨어 개발, 조선, 건설 등 다양한 도메인의 워크플로우 관리에 유연하게 활용될 수 있는 확장성(Extensibility)을 제공한다.

마) 변경 이력의 추적성 확보
SAL ID 체인을 통해 작업 변경 이력이 불변 보존되므로, 필요한 경우 과거 상태 복원 및 원인 규명이 가능하다.

【도 4】 본 발명의 파서 모듈(40) 동작 흐름도 (SAL ID 파싱 프로세스)
【도 5】 본 발명의 SAL 그리드 생성 프로세스 흐름도 (22개 속성 그리드 자동 생성)
【도 6】 본 발명의 SAL 그리드 기록 및 뷰어 시스템 구조도
【도 7】 본 발명의 SAL ID 체인 모듈 구조도 (변경 이력 관리)
【도 8】 본 발명의 멀티태스크 오케스트레이션 시스템 화면 (9단계 순환 프로세스)

【발명을 실시하기 위한 구체적인 내용】
이하, 첨부 도면을 참조하여 본 발명의 바람직한 실시예를 상세히 설명한다.

1. 전체 시스템 구성 (도 1 관련)
도 1은 본 발명의 실시예에 따른 멀티태스크 오케스트레이션 시스템의 전체 구성도를 도시한다.

본 시스템은 SAL ID(식별자)라는 간단한 텍스트 입력만으로 프로젝트의 3차원 그리드 구조 및 작업 간 의존성이 자동으로 생성되는 초고효율 모델링 인터페이스를 특징으로 한다. 종래 방식에서는 작업 생성 시마다 선행 작업과 후행 작업을 수동으로 연결해야 했으나, 본 발명은 SAL ID의 좌표 정보만으로 이러한 관계를 자동으로 추론한다.

1.1 5계층 아키텍처
도 1을 참조하면, 본 시스템은 다음의 5개 계층으로 구성된다:

**계층 1: 입력 계층**
SAL ID 생성 모듈(30)이 프로젝트 작업을 식별하는 고유 식별자를 생성한다. 이 모듈은 사용자 입력 또는 자동 생성 규칙에 따라 SAL ID를 산출한다.

**계층 2: 엔진 계층**
파서 모듈(40)은 입력된 SAL ID를 파싱하여 Stage, Area, Level 좌표를 추출하고 정규화한다. SAL 그리드 생성기(52)는 파싱된 정보를 바탕으로 Task 지시서 및 검증 지시서를 생성한다. 시퀀서(53)는 작업 내용을 분석하여 실행 순서를 조정하고, 배분기(54)는 적절한 에이전트와 도구를 자동으로 할당한다.

**계층 3: SAL 그리드 계층**
기본 정보(51)와 지시서(52)를 바탕으로 Task 실행(84) 및 검증 수행(85)이 진행된다. SAL 그리드 레코더(60)는 실행 및 검증 결과를 실시간으로 기록하며, Stage 검증(87) 단계에서 해당 단계 전체의 완료 여부를 종합적으로 검증한다.

**계층 4: 이력 관리 계층**
SAL ID 체인 모듈(70)은 작업의 이동 및 변경 이력을 블록체인 스타일의 Append-only 체인으로 관리한다. 이를 통해 작업의 모든 변경 사항이 삭제되지 않고 보존되며, 과거 상태를 추적할 수 있다.

**계층 5: 출력 계층**
SAL 그리드 뷰어(63)는 프로젝트 진행 상황을 Stage(X), Area(Y), Level(Z)의 3차원 공간으로 시각화한다. Stage 검증 리포트(88)는 각 단계의 완료 현황, 차단 요소, 품질 지표를 포함하는 종합 리포트를 자동 생성한다.

1.2 데이터 흐름
시스템 내 주요 데이터 흐름은 다음과 같다:
- SAL ID 생성(30) → 파서(40): 식별자 전달
- 파서(40) → 그리드 생성기(52) → 시퀀서(53) → 배분기(54): 순차적 처리
- 엔진 계층 → SAL 그리드 계층: 그리드 구축 및 실행
- 그리드 계층 → 레코더(60) → 뷰어(63): 결과 기록 및 시각화
- 모든 변경 사항 → ID 체인(70): 이력 보존

이러한 계층적 구조는 각 모듈의 역할을 명확히 분리하여 시스템의 유지보수성과 확장성을 보장한다.

2. SAL 그리드 좌표계 (도 2 관련)
도 2는 본 발명의 핵심 기반이 되는 SAL 그리드 좌표계의 개념도를 도시한다.

본 발명의 SAL 그리드(20)는 Stage, Area, Level의 3개 직교 축으로 정의되는 3차원 좌표 공간이다. 이 좌표계는 프로젝트의 모든 작업을 공간적으로 배치하고, 작업 간의 관계를 직관적으로 표현할 수 있는 기반을 제공한다.

도 2를 참조하면, SAL 그리드(20)는 3개의 직교 축으로 정의되는 3차원 좌표 공간이다.

2.1 Stage 축 (21) - X축
Stage는 프로젝트의 개발 진행 단계 또는 공정을 나타내는 X축이다.

Stage는 프로젝트의 시간적 흐름 또는 절차적 단계를 나타낸다. 1~99 범위의 정수 값을 가지며, 낮은 숫자가 프로젝트 초기 단계를, 높은 숫자가 후기 단계를 의미한다. 예를 들어, 소프트웨어 개발 프로젝트에서 S1=기획, S2=설계, S3=개발, S4=테스트, S5=배포와 같이 정의할 수 있다.

2.2 Area 축 (22) - Y축
Area는 업무의 기능적 영역 또는 모듈을 나타내는 Y축이다.

Area는 프로젝트 내의 기능적 영역, 모듈, 부서, 또는 업무 도메인을 나타낸다. 2자리 대문자 알파벳 코드로 표현되며(예: FE=Frontend, BE=Backend, QA=품질보증), 시스템에서 관리하는 코드표에 의해 유효성이 검증된다. 이를 통해 프로젝트의 수평적 분할 구조를 명확히 표현한다.

2.3 Level 축 (23) - Z축
Level은 동일 단계/영역 내의 의존 계층을 나타내는 Z축이다.

Level은 작업 간 의존성과 수행 순서의 계층을 나타낸다. 1~99 범위의 정수 값을 가지며, 낮은 Level의 작업이 선행 작업, 높은 Level의 작업이 후행 작업이 된다. 동일한 Stage와 Area 내에서 Level 값이 낮은 작업이 먼저 완료되어야 높은 Level의 작업을 시작할 수 있다.

2.4 3차원 좌표 공간
이 3축이 정의하는 3차원 공간 상에 SAL 그리드(20)가 배치되며, 각 Task는 (Stage, Area, Level) 튜플로 고유하게 식별되는 좌표계의 특정 위치에 매핑된다. 이러한 3차원 구조는 프로젝트의 시간적 흐름(Stage), 기능적 분할(Area), 의존 관계(Level)를 동시에 표현할 수 있어, 복잡한 프로젝트 구조를 직관적으로 이해할 수 있게 한다.

3. SAL ID (식별자 키) (도 3 관련)
도 3은 Tasks를 식별하는 고유 체계인 SAL ID (식별자)의 구조를 예시적으로 도시한다.
도 3을 참조하면, SAL ID (식별자)는 `S{stage}{AREA}{level}{variant?}` 형식으로 정의된다.
- 접두사 S: SAL ID (식별자) 식별자
- Stage(31): 1~2자리 공정 단계 (예: 1, 99).
- Area(32): 2자리 영역 코드 (예: FE, BE).
- Level(33): 1~2자리 의존 레벨 (예: 1, 10).
- Variant(34): 병렬 작업 구분을 위한 선택적 문자 (예: a, b).
예를 들어 `S2FE2a`는 2단계(Stage 2), Frontend(FE) 영역, 레벨 2 위치의 'a' 작업에 해당한다. 이 식별자는 기계적 파싱 효율성과 인간 가독성을 동시에 만족한다.
4. 파서 (Parser) 모듈 (도 4 관련)
도 4는 입력된 SAL ID를 처리하는 파서 모듈의 흐름도를 도시한다.
파서 모듈(40)은 입력된 SAL ID(예: `S2FE2a`)를 해석하여 프로세스가 이해하고 실행 가능한 정규화된 좌표 객체로 변환하는 핵심 엔진이다. 이 과정은 크게 4단계로 진행되며, 프로세스의 안정성과 시스템 무결성을 보장한다.

4.1 입력 (Input)
ID 생성 모듈(30)로부터 `S2FE2a`와 같은 원시 문자열(Raw String)을 입력받는다. 이 문자열에는 Stage(단계), Area(영역), Level(레벨), Variant(변형) 정보가 압축되어 있다.

4.2 프로세스 단계 (Process Steps)
파싱 프로세스는 다음의 순차적인 검증 단계를 거친다.

1) 정규식 매칭 (Regex Matching): 입력된 ID가 프로세스의 정의된 형식(`^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$`)과 일치하는지 검증한다. 형식에 맞지 않으면 즉시 오류를 처리한다.
2) 범위 검사 (Range Check): 추출된 숫자(Stage, Level)가 유효 범위(1~99) 내에 있는지 확인한다. 범위를 벗어난 단계는 차단한다.
3) 코드 유효성 검사 (Code Validation): 중간의 영문 코드(Area Code)가 `Area_Code_Master`에 등록된 유효한 영역 코드인지 확인한다. 등록되지 않은 코드는 실행할 수 없는 작업으로 간주한다.
4) 정렬 키 생성 (Sort Key Generation): 유효성이 확인되면, 데이터베이스 정렬이나 실행 순서 보장을 위해 고유한 정렬 키(예: `02_FE_02_a`)를 생성한다.

4.3 예외 처리 (Exception Handling)
이 검증 과정 중 어느 하나라도 실패하거나, 매핑되지 않는 ID의 경우 Unassigned Queue(46)로 이동된다. 이는 프로세스를 중단시키지 않고, 해당 작업을 '대기열'에 넣어 관리자가 수동으로 재정의하거나 해결할 수 있도록 하는 안전장치이다.

4.4 출력 (Output)
모든 검증을 통과하면 파싱된 객체(Parsed Object)가 생성된다. 이 객체는 다음 단계인 SAL 그리드 생성기(52)에 전달되어, 개별 작업 지시서(Task Instruction) 및 검증 지시서를 만드는 기초 데이터로 사용된다.

요약하자면, 파서 프로세스는 "불완전한 문자열을 실행 가능한 완벽한 명령어로 변환하고 오류는 별도로 격리하여 시스템 흐름에 영향을 주지 않는 과정"으로 정의된다.

5. 그리드 생성 프로세스 (도 5 관련)
도 5는 그리드를 생성하는 순차적 프로세스를 도시한다.

5.1 기본 정보 입력 (51)
프로젝트 실행에 필요한 핵심 정보인 Stage(단계), Area(영역), Level(레벨), Task Name(작업명), SAL ID(식별자)가 입력된다.

5.2 SAL 그리드 생성기 및 지시서 생성 (52)
5.2 SAL 그리드 생성기 및 지시서 생성 (52)
SAL 그리드 생성기(52)는 입력된 정보를 바탕으로 Task 지시서(Task Instruction) 및 검증 지시서(Verification Instruction)를 생성한다.

5.2.1 점진적 의존성 갱신 (Incremental Dependency Update)
특정 SAL ID의 변경이 필요한 경우(When Needed), 시스템은 전체 그리드를 다시 생성하지 않고, 해당 식별자(SAL ID)를 가진 작업(Task)과 이와 의존 관계(Dependency)로 연결된 후행 작업들만을 추출하여, 이들의 정적/동적 속성을 선택적으로 갱신(Selective Update)하는 최적화 프로세스를 수행한다. 이를 통해 대규모 프로젝트에서도 실시간 반응성을 확보한다.

5.3 시퀀서: SAL ID 조정 (53)
시퀀서(53)는 Task의 내용(Content)을 분석하여 실행 순서를 조정하고 충돌을 방지하여 최적화한다.

5.4 배분기: 자원 배분 (54)
배분기(54)는 그리드 속성 중 '5. Task 지시서(Task Instruction)'의 내용을 정밀 분석하여, 해당 작업을 수행하는 데 필요한 '최적의 에이전트(6. Task Agent)'와 '적절한 도구(7. Tools)'를 자동으로 식별하고 매칭(Binding)하는 역할을 수행한다.

5.5 SAL 그리드 완성 (55)
모든 과정이 완료되면 SAL 그리드 객체가 최종 완성된다. 이 그리드는 실시예에 따라 22개 내외의 속성으로 구성될 수 있다.

5.6 SAL Grid 22개 속성 상세 (예시)
본 발명의 일 실시예에서, SAL Grid는 다음 6개 그룹의 22개 속성을 포함할 수 있다. 이는 예시적 구성이며, 도메인에 따라 가감될 수 있다.

(1) 기본 정보 (Basic Info)
1. **Stage (단계)**: 프로젝트의 진행 단계 (Integer, 예: 1)
2. **Area (영역)**: 기능적 영역 코드 (String, 예: "FE")
3. **Task ID**: SAL ID와 동일한 식별자 (String, 예: "S1FE1a")
4. **Task Name**: 인간 가독형 작업명 (String, 예: "Login UI Dev")

(2) 작업 지시 (Task Instruction)
5. **Task 지시서**: 구체적인 Task 지시 사항 (String/Data)
6. **Task Agent**: 작업을 수행할 주체 (String, 예: "Claude 3.5")
7. **Tools**: 작업에 필요한 도구 목록 (List, 예: ["VS Code", "React"])
8. **Execution Type**: 실행 방식 (String, 예: "Manual", "Auto")
9. **Dependencies**: 선행 작업 ID 목록 (List<String>)

(3) 작업 실행 (Task Execution)
10. **Task Progress**: 진행률 (Percentage, 0~100)
11. **Task Status**: 현재 상태 (Enum: Pending, Running, Done, Failed)
12. **Generated Files**: 산출물 파일 경로 목록 (List<Path>)
13. **Modification History**: 변경 이력 로그 (List<Log>)

(4) 검증 지시 (Verification Instruction)
14. **Verification Instruction**: 검증 기준 및 절차 (String)
15. **Verification Agent**: 검증을 수행할 주체 (String, 예: "TestRunner")

(5) 검증 실행 (Verification Execution)
16. **Test**: 단위 테스트 실행 결과 (Boolean/String)
17. **Build**: 빌드 성공 여부 (Boolean)
18. **Integration Verification**: 통합 테스트 결과 (Boolean)
19. **Blockers**: 진행을 막는 방해 요소 (String)

(6) 검증 완료 (Verification Completion)
20. **Comprehensive Verification**: 종합 검증 결과 (Boolean)
21. **Verification Status**: 검증 상태 (Enum: Unverified, Verified)
22. **Remarks**: 특이사항 및 비고 (String)

6. SAL 그리드 기록 및 뷰어 시스템 (도 6 관련)
도 6은 본 발명의 실시예에 따른 SAL 그리드 기록기(60)가 데이터를 시각화하는 뷰어 프로세스의 계층적 아키텍처를 도시한다.
이 프로세스는 시스템의 견고성을 보장하기 위해 다음 3계층(3-Layer) 구조로 설계되었다.

6.1 데이터베이스 시스템(61)
이 계층은 기록기 및 뷰어가 참조할 원천 데이터를 정의한다. 시스템의 구축 환경이나 보안 요구사항에 따라 데이터베이스(관계형 DB) 또는 파일 시스템(JSON/XML) 중 하나를 선택적으로 사용할 수 있는 어댑터 인터페이스를 제공한다.
이를 통해, 중앙 집중식 관리가 필요한 기업 환경(DB)과 분산 버전 관리가 필요한 오픈소스 환경(File/Git)을 모두 지원할 수 있다.

6.2 뷰어 엔진 (62)
*   Data Loader: 선택된 데이터베이스로부터 원시 데이터를 비동기적으로 로드하여 State Parser에 전달한다.
*   State Parser: 로드된 데이터에서 Task의 상태(Status), 진행률(Progress), 검증 결과(Verification Result)를 파싱하여 시각화 가능한 객체 모델로 변환한다.

6.3 UI 렌더링 시스템(63)
*   3D Canvas: State Parser로부터 변환된 데이터를 수신하여 3차원 그리드 형태로 렌더링한다.
*   Dashboard: 프로젝트의 각 단계(Stage) 완료 시점의 공개 데이터를 직관적으로 표시한다.
이 UI 렌더링 시스템(63)은 SAL 그리드 뷰어의 핵심 기능을 수행하며, "단편적인 리스트 뷰에서는 파악하기 힘든 작업의 시공간적 위상(Spatio-temporal Topology)을 시각화한다. Stage(시간), Area(공간), Level(계층)의 3축 상에 작업을 배치함으로써, 사용자가 해당 작업이 전체 프로젝트의 어느 흐름(Flow)과 위치(Position)에 존재하는지를 직관적으로 인지하는 '다차원 맥락 인지(Multidimensional Context Awareness)' 환경을 제공한다."

7. SAL ID 체인 관리 모듈 (도 7 관련)
도 7은 SAL ID 체인 모듈(70)의 시스템 구조 및 관리 방식을 도시한다.

Task의 SAL ID는 변경될 수 있다. SAL ID가 변경된다는 것은 해당 Task가 3차원 SAL 그리드 상에서 이동했음을 의미한다 (Stage, Area, Level 중 하나 이상 변경). SAL ID 체인 모듈은 이러한 ID 변경(이동) 이력을 관리한다.

7.1 SAL ID 체인 목록 (71)
Task의 SAL ID가 변경될 때마다 변경 이력을 체인 형태로 기록한다. 도 7의 예시에서 S1A1 → S2A1 → S2B2와 같이 기록된다. 체인의 마지막 세그먼트가 해당 Task의 최신 SAL ID(72)이다.

7.2 체인 덧붙이기 (73)
SAL ID가 변경될 때 기존 ID를 삭제하지 않고 새로운 ID를 체인에 덧붙인다(Append). 도면에 표시된 바와 같이 Append-Only 방식으로 동작한다.

7.3 리졸버(74) 및 자가 치유(Self-Healing)
리졸버(74)는 외부 시스템이나 사용자가 구(Old) SAL ID로 작업을 조회할 때, SAL ID 체인 목록을 순회하여 현재 활성 상태인 최신 SAL ID(72)를 반환하는 라우팅 기능을 수행한다. 이를 통해 작업의 위치가 변경되어 ID가 바뀌더라도, 기존 참조(Reference)가 깨지지 않고 자동으로 최신 위치로 연결되는 '참조 무결성(Referential Integrity)'과 '자가 치유(Self-Healing)' 메커니즘을 제공한다.

8. 멀티태스크 오케스트레이션 시스템 (도 8 관련)
도 8은 본 시스템의 전체적인 운영 주기를 9단계로 도시하며, 각 단계는 다음과 같은 상세 프로세스를 수행한다.

8.1 계획 수립 (81)
프로젝트 매니저(PO)가 전체 목표를 설정하면, 파서(Parser)가 초기 입력을 분석하고 정규화한다. 이어 시퀀서(Sequencer)가 작업의 순서 및 의존성을 확정하고, 배분기(Distributor)가 최적의 실행 자원을 할당한다.

8.2 SAL ID 생성 (82)
계획된 각 과업을 매트릭스(Stage × Area) 상에 매핑하여 5개 핵심 속성(Stage, Area, Level, ID, Name)을 포함하는 고유한 SAL ID (식별자)를 산출한다. 이 식별자는 이후 모든 추적 및 관리의 기준(Primary Key)이 된다.

8.3 SAL 그리드 구축 (83)
확정된 SAL ID를 기반으로 Task 지시서 및 검증 지시서를 생성하고, 이를 담을 22개 속성의 그리드 객체를 초기화(Initialize)한다. 이때 변경되지 않는 정적 속성(Static Properties)은 미리 기재되어 작업의 효율성을 높인다.

8.4 Task 실행 (84)
할당된 에이전트가 각 Task 지시서에 따라 개별 작업을 수행한다. 실행 중 발생하는 상태 변화(Status), 진행률(Progress), 생성된 파일(Artifacts), 소요 시간(Duration) 등의 동적 속성(Dynamic Properties)은 실시간으로 추적된다.

8.5 검증 수행 (85)
작업이 완료되면 검증 에이전트(Verification Agent)가 투입되어 테스트 결과(`test_result`), 빌드 성공 여부(`build_result`), 코드 품질 등을 검증한다.

8.6 실행 및 검증 결과 기록 (86)
수행 및 검증 결과는 SAL 그리드 기록기를 통해 실시간으로 기록된다.

8.7 Stage 검증 (87)
개별 Task 검증을 넘어, 해당 단계(Stage) 전체의 완료 여부 및 통합성을 종합적으로 검증한다. 모든 하위 Task가 검증(Verified) 상태에 도달했는지 확인한다.

8.8 리포트 생성 (88)
축적된 그리드 데이터 및 ID 체인 로그를 분석하여, 각 Task의 상세 현황, 차단 요소(Blockers), AI 분석 인사이트를 포함하는 종합 검증 리포트를 자동 생성한다.

8.9 Stage 승인 (89) (Stage Gate)
생성된 리포트를 기반으로 다음 단계(Next Stage)로의 진입 여부를 최종 승인한다. 만약 승인이 거절(반려)될 경우, 프로세스는 Task 실행(84) 단계로 회귀(Loopback)하여 수정된 프로세스를 재실행한다.

이상과 같이 설명된 본 발명은 3차원 좌표계와 불변 ID 체인을 결합하여 멀티 에이전트 시스템(Multi-Agent System)의 복잡한 작업을 완벽하게 통제하고 자동화하는 혁신적인 멀티태스크 오케스트레이션 아키텍처를 제공한다.

【산업상 이용가능성】
본 발명은 다수의 프로젝트를 통합 관리하거나, 복잡한 프로젝트의 체계적인 관리가 필수적인 다양한 산업 분야에 폭넓게 이용될 수 있다. 특히 다음의 5가지 분야에서 그 효율성이 두드러진다.

첫째, 소프트웨어 개발(Software Development) 분야에 적용된다. 복잡한 마이크로서비스 아키텍처(MSA) 환경에서 빌드, 테스트, 배포 파이프라인을 관리하는 데 있어, 각 서비스의 배포 단계를 3차원 그리드에 매핑하여 시각화함으로써 서비스 간의 의존성 충돌을 사전에 방지하고 배포 병목 구간을 신속하게 파악할 수 있다.

둘째, 대형 제조(Large-scale Manufacturing) 및 선박 건조(Shipbuilding) 분야에 적용된다. 선박이나 대형 플랜트와 같이 수만 개의 부품과 공정이 복잡하게 얽힌 제조 현장에서, 블록 조립 및 의장 작업을 3차원 좌표계로 체계화하여 관리한다. 이를 통해 공정 간의 물리적, 시간적 간섭을 시뮬레이션하여 리스크를 최소화하고, 각 부품의 품질 검사 이력을 체인으로 추적하여 제품의 신뢰도를 높인다.

셋째, 건설(Construction) 및 인프라 구축 분야에 적용된다. 고층 빌딩이나 도로, 교량 건설과 같은 대형 인프라 프로젝트에서 토목, 골조, 마감 등 시공 단계와 공구(Zone)별 작업을 입체적으로 관리한다. 이는 다수의 협력사가 투입되는 현장에서 작업 간섭을 방지하고 자재 투입 시점을 최적화하여 전체 공사 기간을 단축하는 데 기여한다.

넷째, 회계감사(Accounting Audit) 분야에 적용된다. 기업의 회계감사 수행 시, 재무제표의 각 계정 과목 및 필수 감사 절차를 그리드 상의 작업으로 정의하여 관리한다. 감사인의 수행 내역과 승인 과정이 블록체인 방식의 체인에 기록되므로 위변조가 불가능하며, 이를 통해 투명하고 신뢰할 수 있는 완벽한 감사 증적(Audit Trail)을 확보할 수 있다.

다섯째, 영화 및 드라마 제작(Media Production) 분야에 적용된다. 프리프로덕션, 프로덕션, 포스트프로덕션으로 이어지는 콘텐츠 제작 과정에서, 씬(Scene), 장소, 배우, 촬영 스케줄을 3차원적으로 구조화하여 관리한다. 이는 복잡한 촬영 일정을 효율적으로 조정하고 자원 낭비를 막아 제작비 절감 및 콘텐츠 완성도 향상에 기여한다.
【특허청구범위】

【청구항 1】
SAL 3D Grid 기반 작업 오케스트레이션 방법에 있어서,
(a) 컴퓨터 시스템이, Stage, Area, Level의 3축으로 정의되는 SAL 3D Grid 좌표계 상에서 작업을 식별하기 위한 SAL ID를 수신하여, 정규식 또는 BNF 문법에 기초하여 상기 SAL ID를 파싱하고, Stage, Area, Level, 및 선택적 Variant 구성요소를 추출하여 정규화하는 단계;
(b) 상기 컴퓨터 시스템이, 상기 파싱 결과로부터 복수의 속성으로 구성된 프로젝트 그리드(SAL Grid)를 생성하고, 동일한 Stage, Area, Level을 갖는 Cell 내의 복수 작업은 상호 의존 엣지 없이 병렬 실행 가능하도록 처리하며, 동일 Stage 및 Area 내에서 Level 증가 방향을 후행 의존으로 간주하고, 외부 의존 목록을 병합하여 DAG(Directed Acyclic Graph)를 자동 생성하는 단계;
(c) 상기 컴퓨터 시스템이, 생성된 DAG에 대해 위상정렬을 수행하고, 자원 제약, 우선순위, 마감 기한을 고려하여 병렬 슬롯팅 및 레벨 재배치를 수행하며, 비용함수를 최소화하는 스케줄을 산출하는 단계;
(d) 상기 컴퓨터 시스템이, 상기 스케줄 결과를 Stage를 X축, Area를 Y축, Level을 Z축으로 하는 SAL 3D Grid에 매핑하여 시각화하는 단계;
(e) 상기 컴퓨터 시스템이, 작업의 이동 또는 변경이 발생하면, 새로운 SAL ID를 생성하여 기존 SAL ID 뒤에 언더바 구분자로 연결하는 블록체인 스타일 ID 체인을 갱신하되, 상기 체인은 추가만 가능하고 중간 삽입, 삭제, 수정이 금지되는 append-only 구조인 단계;
(f) 상기 컴퓨터 시스템이, 상기 체인의 마지막 SAL ID를 현재 실행 노드로 취급하여 상기 DAG, 스케줄, 및 시각화를 갱신하는 단계; 및
(g) 상기 컴퓨터 시스템이, 진행 현황, 병목 탐지, KPI, 예측, 시나리오 비교를 포함하는 리포트를 자동 생성하는 단계;
를 포함하는 방법.

【청구항 2】
청구항 1의 방법을 수행하기 위한 SAL 3D Grid 기반 작업 오케스트레이션 시스템에 있어서,
SAL ID를 수신하여 정규식 또는 BNF 문법에 기초하여 파싱하고, Stage, Area, Level, Variant 구성요소를 추출하며, 코드표 유효성 검사 및 고유키 충돌 방지를 수행하고, 정렬키를 생성하는 Parser/Normalizer 모듈;
파싱된 SAL ID로부터 Task 지시서 및 검증 지시서를 생성하고, 복수의 속성으로 구성된 SAL Grid를 생성하며, 동일 Cell 병렬 규칙, Level 후행 규칙, 외부 의존 병합 규칙에 의해 DAG를 자동 구성하고, 순환을 검출하며, 병목 후보를 마킹하는 SAL 그리드 생성기 모듈;
DAG에 대해 위상정렬, 자원 제약 기반 슬롯 할당, 비용함수 최적화, 레벨 재배치를 수행하는 Scheduler/Leveler 모듈;
스케줄 결과를 Stage=X, Area=Y, Level=Z의 3D 좌표에 매핑하고, 사용자 상호작용에 따른 폐루프 처리를 수행하는 3D Renderer/UI 모듈;
작업 이동/변경 시 SAL ID를 언더바로 연결하여 append-only 체인을 관리하고, chain_text, chain_list, current_id를 저장하며, 감사 로그를 기록하고, 과거 ID 참조를 최신 ID로 해석하는 리졸버를 포함하는 ID Chain 관리 모듈; 및

【요약서】

【요약】
본 발명은 프로젝트의 Stage(단계)와 Area(영역)로 구성된 매트릭스 상에서 Task(작업)를 식별하여 Level(계층) 및 Variant(병렬 분기)를 부여하고, 이들 정보를 인코딩하여 SAL ID(식별자)를 생성한다. 생성된 SAL ID는 절차적 순서와, 실행적 선후 관계의 의존성, 병렬성 및 인접성 정보를 구조적으로 내재하고 있다.

생성된 SAL ID를 파서가 파싱하여 3차원 좌표(Stage, Area, Level)를 추출하고, SAL 그리드 생성기가 Task 및 검증 지시서를 생성하며, 시퀀서가 SAL ID를 조정하고 배분기가 에이전트와 도구를 배분하여 복수의 속성으로 구성된 프로젝트 SAL 그리드를 구축한다.

이렇게 구축된 SAL 그리드를 포함하는 멀티 태스크 오케스트레이션 시스템은, SAL ID 생성 모듈, 파서 모듈, SAL 그리드 생성기, 시퀀서, 배분기, 그리고 Task 실행 및 검증 수행 결과를 기록하는 SAL 그리드 레코더, 프로젝트 진행상황을 실시간으로 시각화하여 보여주는 SAL 그리드 뷰어 등으로 구성된다.

또한, 본 시스템에 따른 오케스트레이션은 계획 수립부터 시작하여, SAL ID 생성, Task 및 검증 지시서 생성, Task 실행, 검증 수행, 실행 및 검증 결과 기록, Stage 검증, 검증 리포트 생성을 거쳐 Stage 승인이 이루어지고 나서 그 다음 Stage가 똑같은 방식으로 진행되는 순환적 프로세스 형태를 갖추고 있다.

위와 같은 멀티 태스크 오케스트레이션 시스템은, 특정 프로젝트 수행에 필요한 다수의 복잡한 작업을 최적화된 방식으로 진행하고 그 과정에 대한 관리, 통제 및 검증을 자동화함으로써 효율성과 효과성을 극대화하고 결과물의 품질을 높게 만든다.
