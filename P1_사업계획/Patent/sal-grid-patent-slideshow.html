기존 기술의 구조적 한계

현재 프로젝트 관리 도구들은 의존성 정의, 식별자 구조, 검증 통합 세 가지 영역에서 근본적인 한계를 갖는다.

  • Airflow — 의존성을 task_a >> task_b 형태로 Python 코드에 직접 선언해야 함. Task가 100개면 의존성 코드도 100줄 이상. 비개발자 접근 불가
  • Jira / Asana — 식별자(PROJECT-1234)는 순차 번호에 불과. 식별자만으로 작업의 단계·영역·우선순위 파악 불가. 별도 라벨·필드에 의존
  • 간트 차트 — 시간(X축) × 작업명(Y축)의 2차원 한계. 수백~수천 개 작업의 입체적 관계를 평면에서 표현 불가
  • 공통 문제 — Task 실행과 품질 검증이 별개 시스템으로 분리 운영. "개발 완료" 후 검증 누락이 구조적으로 발생

SAL Grid 방법론

SAL Grid는 식별자 하나에 3차원 좌표(Stage, Area, Level)를 인코딩하고, 이를 파싱하여 프로젝트 관리 구조 전체를 자동 구축하는 방법론이다.

핵심 발상: 의존성은 선언하는 것이 아니라, 식별자에서 읽어내는 것이다.
  • SAL ID 파싱 → 22개 속성의 프로젝트 그리드 자동 구축
  • Task 지시서 + 검증 지시서 동시 생성
  • 에이전트·도구 자동 배정, 9단계 사이클 자동 구동
  • 코딩 없이 식별자 하나로 프로젝트 관리 체계 완성

SAL ID 형식 정의

S{Stage}{Area}{Level}{Variant?}

  S       — 접두사 (고정)
  Stage   — 1~2자리 정수. 프로젝트 진행 단계
  Area    — 2자리 영문 대문자. 기능적 영역 코드
  Level   — 1~2자리 정수. 의존성 계층
  Variant — 소문자 a~z (선택). 병렬 분기

S2BA3 = Stage 2, Backend API, Level 3
S1FE1a = Stage 1, Frontend, Level 1, 첫 번째 병렬 분기

Jira의 PROJECT-1234(순차 번호)와 달리, 식별자를 읽는 것만으로 작업의 위치와 맥락을 즉시 파악할 수 있다.

SAL ID에 인코딩된 4가지 정보

① 절차적 순서
Stage 값 대소 비교로 순서 자동 결정
S1 → S2 → S3
② 실행 의존성
동일 Stage-Area 내 Level 비교로 선후 관계 추론
S2BA1 → S2BA2 → S2BA3
③ 병렬성
Variant(a, b, c)로 병렬 실행 판별
S2BA1a와 S2BA1b 동시 수행
④ 기능적 인접성
동일 Stage-Area 조합의 Task는 같은 맥락 공유
S2BA1, S2BA2, S2BA3 = 같은 기능군

SAL ID 파싱 정규식

^S(\d{1,2})([A-Z]{2})(\d{1,2})([a-z])?$
  • 캡처 그룹 1: Stage — 캡처 그룹 2: Area — 캡처 그룹 3: Level — 캡처 그룹 4: Variant
  • 정규식 하나로 유효성 검증 + 구성요소 추출 동시 수행
  • 이후 범위 검사 → Area 코드 등록 확인 → 고유성 검사 → 정규화된 좌표 객체 생성
이 파싱이 SAL Grid 방법론의 출발점이다. 문자열 → 구조화된 좌표 변환 → 프로젝트 그리드 자동 구축 시작.

3차원 좌표계 ① Stage 축

프로젝트의 시간적 진행 단계를 나타낸다. 1~99 범위의 정수로 최대 99개 단계 정의 가능.

  • 낮은 숫자 = 초기 단계, 높은 숫자 = 후기 단계. 대소 비교만으로 순서 결정
  • SW 개발: S1=기획, S2=설계, S3=개발, S4=테스트, S5=배포
  • 건설: S1=설계, S2=조달, S3=시공, S4=검수, S5=인도
  • 도메인에 따라 Stage 정의만 바꾸면 동일 시스템 적용. 산업 비종속적 구조
Stage 값의 대소 비교만으로 프로젝트 전체의 절차적 순서가 자동 결정된다. 별도 일정표나 DAG 선언 없이, 식별자 자체가 순서를 내포한다.

3차원 좌표계 ② Area 축

프로젝트 내의 기능적 영역을 나타낸다. 2자리 영문 대문자 코드로 최대 676개(26×26) 영역 정의 가능.

  • FE(Frontend), BE(Backend), QA, SE(Security), DA(Data), DB(Database) 등 프로젝트 특성에 맞게 자유롭게 정의
  • Area 코드 → 에이전트 자동 배정 기준. FE → frontend-developer, SE → security-specialist 등 역할 자동 매핑
  • 작업 에이전트 ≠ 검증 에이전트 — 작성자 ≠ 검증자 원칙이 시스템 레벨에서 구조적으로 강제됨
  • 동일 Stage의 서로 다른 Area 작업은 병렬 실행 가능 — Stage 간 순서만 보장하면 Area 간은 독립적

3차원 좌표계 ③ Level 축

동일 Stage-Area 셀 내에서 의존성과 수행 순서를 결정하는 세 번째 축. 1~99 범위 정수.

  • Level 작은 값 = 선행, 큰 값 = 후행. S2BA1 → S2BA2 → S2BA3 순서 자동 결정
  • 같은 Area 내: Level 값의 대소 비교로 의존성 자동 추론 — 별도 선언 불필요
  • 다른 Area 간: dependencies 필드로 명시적 선언 — 교차 영역 의존성 처리
  • 자동 추론(같은 Area) + 명시적 선언(다른 Area)의 이중 구조로 유연성과 정확성 동시 확보
Level 축 덕분에 하나의 셀(Stage × Area) 안에서도 세밀한 작업 순서 제어가 가능하다.

Stage × Area 매트릭스

모든 작업은 Stage(X축) × Area(Y축) 2차원 매트릭스 위에 배치되며, 각 셀 안에서 Level이 깊이를 부여하여 3차원 구조를 형성한다.

  • Stage 범위 + Area 범위 정의 → 매트릭스 셀(교차점)이 작업 영역. 예: 5 Stage × 11 Area = 55개 셀
  • 각 셀 안에서 Level + Variant 부여 → SAL ID 확정. 하나의 셀에 여러 Task 배치 가능
  • 매트릭스를 그리고 Task를 배치하면 → 의존성, 에이전트 배정, 지시서, 검증 체계가 자동 완성
  • 매트릭스 시각화를 통해 프로젝트 전체 구조를 한눈에 조망 가능
SSAL Works 적용 사례: 5 Stage × 11 Area = 55 셀에 총 71개 Task 배치. 매트릭스만 보면 진행 현황, 병목, 의존 관계를 즉시 파악.

핵심 차별점 ① 의존성 자동 추론

기존 워크플로우 시스템은 의존성을 사람이 직접 선언해야 한다. SAL Grid는 이 전제를 뒤집는다.

  • Airflow: Task 100개면 의존성 코드 100줄 이상 수동 작성
  • SAL Grid: S2BA1, S2BA2, S2BA3 ID만 부여하면 Level 비교로 순서 자동 결정
  • S1 모든 Task는 S2 Task보다 선행 — Stage 비교로 자동 추론
"의존성 선언을 자동화"한 것이 아니다. 의존성이라는 개념 자체를 식별자의 구조적 속성으로 치환한 것이다.

핵심 차별점 ① Airflow와의 결정적 차이

Apache Airflow

  • DAG를 Python 코드로 작성
  • task_a >> task_b 수동 선언 필수
  • 프로그래밍 지식 필수
  • 식별자에 구조 정보 없음
VS

SAL Grid

  • SAL ID 부여만으로 의존성 추론
  • 코딩 불필요
  • 비개발자도 즉시 활용
  • 식별자에 3차원 좌표 인코딩

핵심 차별점 ② 프로젝트 그리드 자동 구축

SAL ID 하나를 파싱하면 22개 속성의 프로젝트 관리 그리드가 자동 완성된다.

핵심 차별점 ② 지시서 자동 생성

SAL ID를 기반으로 Task 지시서와 검증 지시서가 쌍으로 동시 생성된다.

Task 지시서

  • Task Goal, Prerequisites, Dependencies
  • 수행 지침, 예상 산출물, 완료 기준
  • Tech Stack, Agent, Tools 자동 배정
  • 참조해야 할 규칙 파일 목록

검증 지시서

  • Verification Criteria (통과 기준)
  • Test Commands (실행할 테스트)
  • Build·Integration 검증 항목
  • 검증 에이전트 지정 (작업자 ≠ 검증자)
Task 지시서와 검증 지시서가 동시에 생성되므로, "작업은 했는데 검증 기준이 없다"는 상황이 구조적으로 불가능하다.

핵심 차별점 ③ ID 체인 — Append-Only

SAL ID가 변경되어도 기존 ID를 삭제하지 않고 뒤에 연결하여 이력을 보존한다.

S4BI1 → S1BI2로 변경 시:  S4BI1_S1BI2
한 번 더 변경 시:          S4BI1_S1BI2_S1BI3
마지막 세그먼트 = 최신 ID, 체인 전체 = 변경 이력
  • 추가만 가능, 삭제·수정 불가 — 블록체인과 동일 원리
  • 변경 이력의 위변조가 구조적으로 불가능

핵심 차별점 ③ 리졸버 — 자가 치유

구(Old) SAL ID로 조회해도, 리졸버가 체인을 순회하여 최신 ID를 자동 반환한다.

  • Jira: Issue 이동 시 기존 참조 링크 전부 깨짐 → 수동 복구 필요
  • SAL Grid: S4BI1로 조회 → 리졸버가 체인 순회 → S1BI3(최신) 자동 반환
참조 무결성의 자가 치유(Self-Healing Referential Integrity) — 프로젝트 구조가 아무리 변경되어도, 한 번 생성된 참조는 영구 유효.

핵심 차별점 ④ 실행-검증 일체화

Task 완료와 동시에 검증이 자동 트리거되며, 작성자 ≠ 검증자 분리 배정이 시스템 레벨에서 강제된다.

  • 기존: Jira에서 "완료" 클릭 → 별도 QA 도구로 이동 → 결과를 다시 Jira에 수동 기록 (검증 누락 빈번)
  • SAL Grid: Executed 상태 전환 → 검증 에이전트 자동 투입 → 4개 검증 항목(Test, Build, Integration, Blocker) 결과 실시간 기록
  • Verified 아닌 Task는 Completed 전환 불가 — DB 트리거로 강제. 검증 우회 구조적 불가
  • 상태 전이: Pending → In Progress → Executed → (Verified 후) Completed. 단계 건너뛰기 불가

핵심 차별점 ④ Stage Gate

개별 Task 검증에 더하여, Stage 단위 최종 승인 절차가 존재한다.

  • Stage 내 모든 Task Completed 확인
  • 전체 빌드·테스트 통과 확인
  • 의존성 체인 완결성 + 차단 요소 확인
  • 승인 → 다음 Stage 진입 / 거절 → Task 실행 단계로 자동 회귀
Jira에는 Stage Gate 개념이 없다. "Done"으로 옮기면 끝. SAL Grid의 Stage Gate는 시스템 레벨에서 강제되는 품질 관문이다.

왜 기존 기술로 도달할 수 없는가

  • 기존 통념: "의존성은 코드로 선언해야 한다" — Airflow 문서, 논문, 상용 도구 전반의 암묵적 전제
  • 기존 개선 방향: 의존성 선언을 "더 편하게", "더 직관적으로" → 선언 자체를 없앤다는 발상에 도달 불가
  • SAL Grid의 접근: 식별자에 좌표를 인코딩하고, 좌표의 대소 비교로 의존성을 추론 → 식별자가 자기 설명적 객체로 재정의됨
이것은 점진적 기술 개선이 아니라, 설계 패러다임의 전환이다.

사이클 ①~③ 계획 → ID 생성 → 그리드 구축

프로젝트 관리 체계를 설계하는 단계. 매트릭스 위에 작업을 배치하고, ID를 부여하면 나머지는 자동 완성.

  • ① 계획 수립: Stage × Area 매트릭스에서 필요한 작업을 선정하고 셀에 배치. 프로젝트 전체 구조를 시각적으로 설계
  • ② SAL ID 생성: 각 Task에 SAL ID 가확정(Provisional) → 의존성 방향 검증 → 순환 참조 체크 → 최종 확정(Finalization)
  • ③ 그리드 구축: 정규식 파싱 → 범위 검사 → Area 코드 유효성 → ID 고유성 검증 → 22개 속성의 프로젝트 그리드 자동 생성
이 세 단계를 거치면 코딩 한 줄 없이 Task 지시서, 검증 지시서, 에이전트 배정, 의존성 체계가 모두 완성된다.

사이클 ④~⑥ 실행 → 검증 → 기록

실제 작업이 수행되고 품질이 확보되는 핵심 실행 단계. 실행-검증-기록이 하나의 연속 프로세스로 작동.

  • ④ Task 실행: 지시서에 따라 에이전트가 작업 수행. 상태(Pending → In Progress → Executed), 진행률, 산출물을 실시간 추적
  • ⑤ 검증 수행: Executed 상태 전환 즉시 검증 에이전트 자동 투입. 단위 테스트, 빌드 검증, 통합 검증, 차단 요소 4개 항목 자동 점검
  • ⑥ 결과 기록: 실행·검증 결과를 원자적 쓰기(Atomic Write)로 그리드에 기록. 부분 기록이나 데이터 불일치 방지
실행과 검증 사이에 인간의 개입이 없다. Task 완료 → 검증 → 기록이 하나의 연속 자동 프로세스로 작동하므로 검증 누락이 구조적으로 불가능.

사이클 ⑦~⑨ Stage 검증 → 리포트 → 승인

개별 Task 검증을 넘어 Stage 전체 단위의 종합 품질 관문. 승인되어야만 다음 Stage로 진입 가능.

  • ⑦ Stage 검증: Stage 내 모든 Task 완료·검증 여부 확인 + 전체 빌드·테스트 통과 + 의존성 체인 완결성 + 차단 요소 종합 점검
  • ⑧ 검증 리포트: Stage 검증 결과를 Task별 현황, 빌드/테스트 결과, AI 의견 등 구조화된 문서로 자동 생성
  • ⑨ Stage 승인: 승인(Approved) → 다음 Stage 사이클 시작 / 거절(Rejected) → ④단계(Task 실행)로 자동 회귀
피드백 루프가 시스템에 내장되어, 결함이 있는 상태로 다음 Stage에 진입하는 것이 구조적으로 불가능하다.

산업 적용 분야

SAL Grid의 3차원 좌표계는 도메인 비종속적 구조이다. Stage와 Area의 정의만 해당 산업에 맞게 바꾸면 동일한 시스템을 그대로 적용할 수 있다.

핵심 차별성 요약

  1. 의존성은 선언하는 것이 아니라, 식별자에서 읽어내는 것이다.
    Stage·Level 값 비교만으로 실행 순서 자동 결정. 선행 사례 없음.
  2. 식별자 하나로 프로젝트 관리 체계 전체가 자동 구축된다.
    22개 속성 그리드 + 지시서 + 검증 지시서 + 에이전트 배정 동시 완성.
  3. 한 번 생성된 참조는 영구적으로 유효하다.
    Append-Only ID 체인 + 리졸버 자동 리디렉트. 참조 깨짐 구조적 불가.
  4. 실행과 검증이 하나의 연속된 자동 프로세스이다.
    Task 완료 → 검증 자동 트리거 → Stage Gate 승인. 시스템 레벨 강제.

특허 청구 범위

본 특허는 시스템 구성요소와 방법론 양 측면에서 청구된다.

시스템 청구항

  • 파서 — SAL ID → 3차원 좌표(Stage, Area, Level) 추출
  • 생성기 — 22개 속성 프로젝트 그리드 자동 구축
  • 시퀀서 — Level 비교 의존성 자동 추론 엔진
  • 배분기 — Area 기반 에이전트 분리 배정 (작업 ≠ 검증)
  • 체인+리졸버 — Append-Only ID 체인 + 자가 치유 참조

방법 청구항

  • 3차원 좌표 인코딩 식별자 파싱 방법
  • 프로젝트 그리드 자동 구축 방법
  • 실행-검증 일체화 사이클 운용 방법
  • Stage Gate 기반 단계별 승인 방법
  • ID 체인 리졸버 자가 치유 방법
